# Architecture Decision Record 001: User Authentication Architecture

The current authentication endpoints, session cookie behavior, and response shapes are maintained in [../api-contract.md](../api-contract.md). This ADR records the identity-provider decision rather than the complete HTTP contract.
## Problem
Nexus in an internal operations service hub intended for mid sized companies of 50-100 employees, currently, they already use a third party identity providers to manage their company email account structure. While designing Nexus, we need to decide how user authentication will operate.

## Options
While deciding the authentication process, two major options were considered:

### In-app User Authentication
Implements the authentication process natively inside Nexus backend, which means Nexus manages user accounts, email verification, passwords hashing, password reset, and client tokens.
#### Pros
- Complete independence from external identity providers
- Flexibility in defining authentication process and features
#### Cons
- Major security risk if authentication feature wasn't correctly implemented
- Credential management risks, if system is breached, user accounts may be exposed, a big security risk
- Introduces significant complexity in building email verification and password reset flows
- Forces companies to keep track of a separate set of account credentials specifically for the app

### Third Party Identity Providers
Handoff authentication to seperate services which offloads user account management from Nexus using strategies for different identity providers.
#### Pros
- Uses existing entreprise level authentication which significantly reduces security risks
- Centralizes account management for companies as only one company account will be used for each user
- Nexus never handles user passwords or credentials
- Simplifies authentication process
#### Cons
- Introduces an external dependancy for Nexus on the identity provider
- Limits companies to using accounts provided by the supported identity providers

## Decision
Nexus will use third party identity providers to manage authentication, initially, Microsoft Entra ID will be implemented, Nexus will have its V0 authentication functions using it. 
Additional identity providers may be implemented in the future.

## Consequences
- Nexus will not manage user passwords, reducing the security risks of credential storage.
- User account management will be centralized through Microsoft Entra ID, allowing companies to manage user access through their existing enterprise identity system.
- Employees will be able to use their existing company accounts to access Nexus without maintaining a separate set of application credentials
- Authentication implementation will be simpler because Nexus can rely on the identity provider for password management, account recovery, email verification, and related security functionality...
- Nexus will become dependent on Microsoft Entra ID for authentication. Complications with the identity provider may prevent users from authenticating.
- The initial implementation will be less suitable for organizations that do not use Microsoft Entra ID.
